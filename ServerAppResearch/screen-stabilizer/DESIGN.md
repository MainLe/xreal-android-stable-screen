# Whole-phone 3/6DoF screen app

Scope: Xiaomi 15 / Android 17 / Air 2 Ultra, rebuilt XREAL Server 1.0.1 and Unity SDK 3.1.0. Application `dev.xreal.stablescreen`, current version 0.4.1, Android API 32+. Earlier version-specific behavior below is historical.

Version 0.4.0 changes the output ownership described in the historical sections below. The app no longer creates an eye Presentation. The SDK owns the sole eye window; a drained offscreen ImageReader retains Unity's primary surface while phone apps change. This addresses the reproduced Android 17 rejection of the SDK's second Presentation. Capture, pose, filtering and target refresh rate remain unchanged. SDK-provider output readiness now gates capture authorization; physical image, motion continuity and background projection require new device validation. See [the evidence and candidate build](DISPLAY-CADENCE.md).

Version 0.4.1 adds a default-on continuous refresh driver within the SDK's existing eye window. On 2026-11-03 the user confirmed smooth static-grid rendering when enabled and severe stutter when disabled, then smooth screen sharing on an idle home screen and across other apps. Keep the compatibility switch enabled for this device. The result validates this output repair on the tested setup; the exact low-level scheduling/cache cause is not established by visual feedback alone. Ordinary phone scrolling with the switch off did not refresh the eye image, so the earlier size-slider observation must not be generalized to all phone UI redraws. No pose or filter change was needed for this successful comparison.

Version 0.3.1 supersedes the default filtering policy below: it uses the raw camera and directly fixed logical anchor by default; optional content compensation is experimental and advances only once per BeforeRender frame. It fixes the <1ms OFF-path reuse defect and unifies tracking validity with the spatial demo. See [the full comparison and long-run investigation](JITTER-AND-LONGRUN.md). Device validation is pending; the user reported residual jitter in 0.3.0 and intermittent spatial-demo degradation with hands enabled.

## Data path

Android's user-consented MediaProjection captures `Display.DEFAULT_DISPLAY`, not the XR external display. Android 14+ uses `MediaProjectionConfig.createConfigForDefaultDisplay()`. A phone-side consent Activity starts a `mediaProjection` foreground service; that service enters foreground before obtaining MediaProjection, registers its callback before creating a VirtualDisplay, and creates that display only once per token. Version 0.3.0 keeps a fixed square surface during orientation changes. Android 12L+ scales the source uniformly and centers it; geometry callbacks change only the content crop. This removes the surface/display dimension race suspected in rare corner-only frames. Explicit quality changes and manual resync replace the surface on the same VirtualDisplay, without reusing the grant for a second display creation.

ImageReader produces RGBA planes. Its worker packs only the centered real phone content into a three-slot direct-buffer mailbox, then immediately closes the Image. Unity borrows one complete frame, copies the contiguous RGBA block into a Texture2D, uploads it, and releases the lease in `finally`. Neither stopping nor replacing an ImageReader invalidates leased memory. A faster producer replaces the queued latest frame; it never modifies a leased frame or accumulates a frame queue. Profiles are 960-pixel long edge / 30 fps, 1200 / 60 (default), and 1600 / 60. A scheduling-tolerant deadline replaces the old fixed 33 ms gate. Surface frame-rate hints are best effort. Source delivery, accepted frames, uploads and eye rendering are measured separately; actual rates require changing source content. The observed stereo glasses mode is 60 Hz; no 90/120 Hz stereo support is claimed.

The Unity texture belongs to a quad whose logical anchor is in world space. The camera reads real SDK rotation in Update and onBeforeRender; position stays zero for 3DoF. The mode control uses XREALPlugin.SwitchTrackingTypeAsync and reports actual native mode separately from requested mode. In 6DoF, valid position tracking is required to show captured content. ARSession and ARInputManager are present in the scene. Recenter places the screen two virtual meters ahead of the current tracked head position. Tracking loss hides captured content until real tracking returns. No synthetic poses substitute for missing tracking.

The supplied SDK public C# API exposes no adjustable head-pose micro-jitter filter found in this investigation. The application's raw camera does not deliberately replace the SDK pose; however, native prediction/warping on the custom primary-surface output has not been verified. The 2026-11-03 device comparison found persistent native FrameWait failures on that path; see [display cadence evidence](DISPLAY-CADENCE.md). StablePoseFilter implements an adaptive low-pass for orientation and position, with small deadbands and bounded correction. Rotation vectors use atan2 of quaternion vector length/w, avoiding acos/ToAngleAxis precision loss at tiny angles. Filtering strength is off/light/balanced/strong. The raw camera pose stays unchanged: for raw pose (p_r,q_r), filtered pose (p_s,q_s), and logical anchor (p_a,q_a), content correction is q_c=q_r*inverse(q_s), p_render=p_r+q_c*(p_a-p_s), q_render=q_c*q_a. Thus the rendered relative view follows the filtered pose without replacing the SDK camera pose. Filtering may add perceived lag; the maximum correction is an algorithmic bound, not a hardware comfort guarantee.

## Background operation

`Application.runInBackground` alone is insufficient on Android. In version 0.2.0, ScreenPlayerActivity remains on display 0 and gives UnityPlayer.displayChanged(0, surface) the surface of a Presentation on the identified glasses display. The visible Presentation owns the player lifetime while the phone switches to its controller, consent dialog, home screen or another app. Screen-off/keyguard and removal pause the player, and removal stops capture. The build disables SDK SupportMultiResume only for this app, and restores the project's shared setting afterwards. No external Activity, system settings mutation, privileged permissions or root is required by this rendering path.

The phone controller and internal Unity host have distinct app-specific task affinities. Old SDK UnityPlayerActivity and NRFakeActivity definitions are removed from this app's manifest. The original external-Activity rejection and subsequent Presentation recovery were confirmed on the phone; details and baseline evidence follow below.

SDK's client-side GlassesDisplayPlugEvent 2.4.2 still requires an HDMI name before reading EDID. This would prevent correct multi-resume display selection on this user's phone. A prepared AAR replaces only DisplayModel.class with the same EDID/name-limited fix used by the rebuilt Server. The SDK source AAR remains unchanged. Replacement applies to the copied Gradle artifact of this app only.

## Lifecycle and controls

The service is non-sticky. Grants are not persisted or reused. Stop, system projection revocation, lock-screen revocation and glasses display removal release capture resources. The consumer blanks/destroys the old texture when capture becomes inactive. Notification actions allow recenter and stop without bringing the controller in front of the source APP. Captured frames have no recording or transmission path. Persistent preferences contain only screen controls, tracking/filter choice and capture quality.

The phone UI reports render fps separately from uploaded source frame fps and rotation validity. Permission success, capture service running and actual stabilized rendering are separate acceptance criteria. The app cannot capture OS-protected content and does not bypass FLAG_SECURE or DRM.

## Verification

`prepare_screen_stabilizer.py`: official AAR digest guard, one-class-only replacement audit, Android Java compilation, pure Java centered crop/row padding/truncation tests, 120 alternating orientation layouts, three-slot lifecycle tests, plus 10000-frame concurrent producer/consumer stress.

`XREALScreenStabilizerBuild`: executes actual Unity NativeArray row-copy checks (including a shortened final row), aspect-fit and recenter geometry checks. StableScreenMotionChecks additionally verifies small-angle jitter attenuation, fast-turn/translation correction bounds, quaternion sign invariance, gap reset, disabled-filter transparency and 6DoF content/camera coordinate equivalence. It then builds shaders, IL2CPP and Android packaging. Temporarily enables only this Android library and restores shared app/SDK settings afterwards. Concurrency is reduced for the 16 GB build host.

`verify_stable_screen.py`: APK version/API/signature/alignment, one correct launcher, MediaProjection foreground-service permission/type, absence of SDK multi-resume Activity classes, single DisplayModel definition, managed capture/filter code, unchanged proprietary native libraries, restored project settings and build-log success. Version 0.3.0 device tests remain pending; previous 0.2.0 results are not reused as evidence for new functionality.

Primary references: [Android MediaProjection scaling and lifecycle](https://developer.android.com/media/grow/media-projection), [Surface.setFrameRate](https://developer.android.com/reference/android/view/Surface#setFrameRate(float,int)), [adaptive low-pass design and tuning](https://gery.casiez.net/1euro/). The quaternion/vector filter here is independently implemented and is not the reference scalar 1€ implementation.

## Version 0.1.1 startup repair and diagnostics

User report for 0.1.0: no Unity splash, `unityReady=false`, zero render fps, overlay permission true, Air 2 Ultra at 3840×1080. This proves scene readiness was not reported and capture had not started; it does not establish whether Java Activity creation or Unity/native initialization failed.

0.1.1 separates all three task affinities, launches through the SDK's public methods directly from the user's foreground Activity, and sets the explicit SDK main-Activity metadata. The Application records the actual creation/resume/display/task of our own Activities before SDK setup. C# reports subsystem entry, pre-splash and scene start before setting ready. Java uncaught exceptions and Unity errors are included in diagnostics. A generation-guarded 20-second watchdog returns to phone controls if the scene has not reported ready; it does not mark the runtime successful or enable capture as a workaround. Copying diagnostics on a worker includes a bounded logcat dump restricted to this app's PID. No ADB connection or READ_LOGS permission is requested.

## Actual 0.1.1 failure and 0.2.0 device evidence

Wireless ADB captured the system rejection: `activity launch is not allowed on a display that cannot host tasks`. The glasses display is physical, trusted and 3840×1080, but `canHostTasks=false`. The phone's actual framework checks this property before allowing the SDK's NRFakeActivity launch. Secure setting `mirror_built_in_display=1` controls that property for this display. Even after ADB security settings allowed changing it, SecondaryDisplayPolicy immediately restored mirroring (`Force enable mirroring`). The setting ended at its original value 1. Changing task affinities alone therefore could not solve startup. The 20-second return in the reported trace was this app's watchdog; that trace did not show a crash.

An existing Server Presentation displayed its full 3840×1080 stereo green grid while the same display still had `canHostTasks=false`. Screenshot evidence: `evidence/stable-screen-presentation-test.png`. Version 0.2.0 applies that standard window path to Unity's primary surface. `evidence/stable-screen-v020-launch.png` shows actual stereo Unity text; startup logs show scene-ready and real rotation, while the phone engine Activity is stopped and the Presentation remains visible. The SDK logs a separate display exception on its old surface path, so scene-ready alone is still not treated as proof of successful output. Actual visual confirmation and the user's stabilization test supply that evidence here.

The report includes Presentation readiness, display/size and old Activity preflight result. `displayStartAllowed=false` is expected under this system mode and is diagnostic only; the app does not attempt that prohibited Activity launch. A separate issue was reproduced when a clean Server 1.0.0 launched its first AR client: client MCU initialization failed with EBUSY / ControlChannelInitFail. Official Control Glasses calls NRServiceControl.onNRPause on its Activity pause and onNRResume on resume. Server 1.0.1 adds that missing ownership handoff and waits for pause success before launching a client; device validation is recorded separately.
